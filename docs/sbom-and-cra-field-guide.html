SBOM and CRA Field Guide

How to produce, manage and use a Software Bill of Materials in a software project, and what the EU Cyber Resilience Act expects from manufacturers. The practices are general; the running example is the IS-Risk Classifier, a Django web application with a CycloneDX SBOM tracked in Dependency-Track.

1 · Basics

What an SBOM is, and what it is for

An SBOM is the parts list of a piece of software: every third-party component with its name, version, a unique identifier and, where possible, a hash and a licence, plus how the components depend on each other. Its value lies in what it enables. When a new vulnerability is published, an SBOM answers within minutes which products and which versions are affected. Without one, the same question takes days of searching through repositories and build logs.

The two common formats

  • CycloneDX (OWASP): security-oriented, covers software, services, hardware, cryptography and vulnerability statements (VEX). Version 1.6 is standardised as ECMA-424.
  • SPDX (Linux Foundation): licence-compliance heritage, standardised as ISO/IEC 5962.

Both are accepted by regulators and tools. This guide uses CycloneDX in JSON.

What an SBOM does not do

  • It does not find vulnerabilities. A scanner matches its identifiers against vulnerability databases.
  • It is a snapshot of one build. A stale SBOM gives false confidence.
  • It lists declared components. Code copied into a package stays invisible.
  • It describes parts, not operation: configuration, network isolation and permissions are out of scope.
2 · Regulation

The EU Cyber Resilience Act

The CRA, Regulation (EU) 2024/2847, sets cybersecurity requirements for products with digital elements placed on the EU market: hardware and software, including software sold or supplied commercially on its own. It makes vulnerability handling a legal obligation for the whole support period, and the SBOM is one of its named tools.

10 Dec 2024Entry into force.
11 Jun 2026Rules for conformity assessment bodies apply.
11 Sep 2026Reporting obligations apply: actively exploited vulnerabilities and severe incidents. Already in effect.
11 Dec 2027All other obligations apply, including the essential requirements and the SBOM.
ObligationWhat it means in practice
SBOM (Annex I, Part II)Identify and document the vulnerabilities and components in the product, including by drawing up an SBOM in a commonly used, machine-readable format, covering at least the top-level dependencies. CycloneDX and SPDX both qualify. The Commission may specify format and minimum elements later by implementing act.
SBOM is not public by defaultThe SBOM belongs to the technical documentation. You must hand it to market surveillance authorities on request; publishing it is your choice.
Vulnerability handling (Annex I, Part II)Address and remediate vulnerabilities without delay, including through security updates; test the product regularly; publicly disclose fixed vulnerabilities; run a coordinated vulnerability disclosure policy with a contact address; distribute updates securely and, for security fixes, free of charge with advisory information.
Third-party componentsExercise due diligence when integrating components, open source included, so they do not compromise the product. Report vulnerabilities you find in an integrated component to whoever maintains it.
Reporting (Art. 14)Actively exploited vulnerabilities and severe incidents go to the national CSIRT and ENISA through the single reporting platform: early warning within 24 hours, notification within 72 hours, final report within 14 days of a fix for vulnerabilities (one month for incidents).
Support periodDetermine it and handle vulnerabilities throughout. As a rule at least five years, unless the product is expected to be used for a shorter time.
Documentation retentionKeep the technical documentation, SBOMs included, for ten years after placing on the market or for the support period, whichever is longer. In practice: archive the SBOM of every released version.
Scope limitsFree and open-source software that is not monetised in the course of a commercial activity is out of scope; open-source stewards have a lighter regime. Some product classes (Annex III, IV) need third-party conformity assessment; the default is self-assessment.

This is an engineering summary, not legal advice. Harmonised standards and implementing acts are still being published and may refine the details. In Germany, BSI TR-03183 already gives concrete guidance: part 2 lists mandatory SBOM fields such as creator, component name and version, dependencies, licence and a SHA-512 hash of each deployable component, and accepts CycloneDX from 1.5 and SPDX.

3 · Process

The SBOM lifecycle

Having an SBOM is a one-off; managing it is a process that repeats with every build. The CRA asks for the process. The steps below apply to any project; the indented notes show how the IS-Risk Classifier does each one.

  1. Generate

    Produce the SBOM automatically in the build, from the same inputs that produce the artifact: the lockfile for application dependencies, the built image for containers. Never write or edit it by hand.

    Example: make sbom runs uv export --format cyclonedx1.5 --frozen --no-dev on uv.lock and adds front-end files and container images from inventories in the repository.

  2. Enrich

    Generators often leave fields empty. Add what the scanner and the regulator need: licences as SPDX IDs, the supplier, hashes of the shipped files, a description of the product itself in metadata.component.

    Example: the Python packages arrive without licences; the front-end entries carry licence and SHA-256 from a checked inventory file.

  3. Validate

    Check the file against the CycloneDX JSON schema and against your own minimum fields before anything consumes it. A tool that silently accepts a broken SBOM is not a validation.

    Example: not yet automated; cyclonedx-cli validate would close the gap.

  4. Sign and archive

    Store the SBOM with the release it describes and keep it for the retention period. Signing (an embedded JSF signature or an attestation, e.g. with Sigstore) lets recipients verify that it was not altered.

    Example: the CI keeps the SBOM as a build artifact for 90 days. Neither signing nor release archiving exists yet.

  5. Distribute

    Upload the SBOM to an analysis platform for every build, versioned like the product. Share it with customers or authorities when they ask.

    Example: uploaded manually to a local Dependency-Track 4.14.5 as project IS-Risk Classifier, version Lock-Stand 22.10.2026.

  6. Monitor

    Vulnerabilities are published after your release. Match every stored SBOM against vulnerability databases continuously, not only at build time, and alert on new findings.

    Example: Dependency-Track matches against OSV; pip-audit and Dependabot add independent checks.

  7. Triage

    Decide for each finding whether it affects the product. Record the decision and its reason as a VEX statement (not_affected, exploitable, resolved, …), so customers and future you can see why. Prioritise with severity plus exploitation signals such as EPSS or the CISA KEV catalogue.

    Example: a policy flags any HIGH or CRITICAL finding as a violation; VEX export is not used yet.

  8. Remediate

    Update the component, ship a security release, publish an advisory, and the cycle starts again with a new SBOM. Under the CRA, an actively exploited vulnerability additionally starts the 24-hour reporting clock.

    Example: a test version with reportlab 3.6.12 (CVE-2023-33733) shows the violation that would trigger the update.

5 · Operations

Operating SBOMs in a team

Platform and automation

  • Use an SBOM platform such as OWASP Dependency-Track: one project per product, one version per release, the latest marked as such.
  • Upload from the CI through the API on every build of a release branch; use the git tag or commit as project version.
  • Enable more than one vulnerability source (OSV, NVD, GitHub Advisories) and alias matching, so the same CVE is not counted twice.
  • Define policies: severity thresholds, forbidden licences, components without a version or purl. Fail the build on violations for new releases.
  • Send notifications to the people who fix things: a team channel, a ticket queue.

Responsibilities and timing

  • Name an owner for each product's SBOM and findings.
  • Set remediation targets per severity and track them. Typical internal targets are days for critical and weeks for high; set your own and write them down.
  • Publish a security contact and a coordinated disclosure policy, for example as /.well-known/security.txt.
  • Rehearse the CRA reporting path once before you need it: who decides that a vulnerability is actively exploited, and who files the 24-hour early warning.
  • Ask your own suppliers for SBOMs, and check them like your own.

8 · Commands

Commands to reuse

Quick look: component count, types, entries without licence or purl
jq '.components | length' bom.cdx.json
jq -r '.components | group_by(.type)[] | "\(.[0].type): \(length)"' bom.cdx.json
jq -r '.components[] | select(.licenses == null) | .purl // .name' bom.cdx.json
jq -r '.components[] | select(.purl == null) | .name' bom.cdx.json
Validate against the schema (CycloneDX CLI)
cyclonedx validate --input-file bom.cdx.json --input-format json --fail-on-errors
SBOM of a container image (Syft)
syft python:3.13-slim-trixie -o cyclonedx-json=image.cdx.json
Upload to Dependency-Track (API key from Administration → Access Management → Teams)
curl -X POST "$DT_URL/api/v1/bom" \
  -H "X-Api-Key: $DT_API_KEY" \
  -F "autoCreate=true" \
  -F "projectName=My Product" \
  -F "projectVersion=$(git describe --tags --always)" \
  -F "bom=@bom.cdx.json"
The example project
make sbom     # writes sbom/is-risk-classifier.cdx.json
make audit    # pip-audit on the runtime dependencies
